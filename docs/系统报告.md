## 1. 项目概述

### 1.1 背景与目标

轴承是铁路列车走行部的核心部件，其运行状态直接关系到列车运行安全。本系统以 **XJTU-SY 轴承全生命周期加速退化数据集**为基础，结合 Gearbox 齿轮箱故障数据集，构建了一套完整的铁路轴承健康状态在线监测与分析原型系统。系统实现了轴承振动数据的多维度可视化、健康状态量化评估、剩余使用寿命（RUL）预测以及多轴承对比分析等功能，为铁路轴承的视情维修（Condition-Based Maintenance）提供数据支撑。

### 1.2 核心功能一览

| 功能模块 | 说明 |
|----------|------|
| 用户认证与权限管理 | 基于 Flask Session 的登录/登出系统，三种角色（管理员/工程师/分析师）分级授权 |
| 系统仪表盘 | 单轴承全景健康视图，含 6 个 ECharts 交互图表 + 健康评估综合报告面板 |
| 轴承详情分析 | 时域波形、振动分布直方图、FFT 频谱（水平/垂直双通道）、RMS 退化趋势、分阶段退化对比、统计特征数据表（分页） |
| 多轴承对比分析 | 2–4 个轴承在 RMS/峰值/峰峰值/波峰因子/健康评分五个维度上的趋势对比、柱状图、雷达图及汇总对比表 |
| 剩余寿命预测（RUL） | 全生命周期 RMS 退化趋势、健康评分退化曲线与预测外推、初期 vs 当前状态对比、仪表盘式可视化、维护建议生成 |
| 数据浏览 | 轴承列表（支持数据集/故障类型/关键词筛选）、工作条件详情卡片、故障类型分布饼图与统计 |

### 1.5 轴承命名规则

- **XJTU-SY 轴承**：`Bearing{工况}_{序号}`，例如 `Bearing1_1` 表示工况 1（35Hz/12kN）下的第 1 个轴承。XJTU-SY 数据集中的轴承从全寿命周期的健康状态开始运行直至完全失效，完整记录了从正常→早期故障→严重故障的退化过程。

## 3. 数据库设计

### 3.1 数据库选型说明

系统选用 SQLite 作为数据存储引擎，原因如下：
1. **零配置部署**：SQLite 无需独立服务进程，作为嵌入式数据库直接集成，简化了原型系统的部署；
2. **大规模数据支撑**：SQLite 支持单表多亿行数据，满足本系统 3.02 亿行振动数据的需求；
3. **查询性能**：通过合理的索引设计和 SQL 优化，核心查询响应时间控制在 3 秒以内。

### 3.2 表结构详细设计

#### 3.2.1 operating_condition（工作条件表）

### 4.2 健康评估算法

系统采用基于 **RMS 振动幅值偏差** 的多维度健康评分模型，核心流程如下：

**Step 1 — 基线计算**：取轴承运行初期（前 2 个采样批次）的水平/垂直 RMS 值作为健康基线。

**Step 2 — 逐批次 RMS 计算**：对每个 `sample_index` 分组计算：
```
RMS_h = SQRT(AVG(horizontal_vibration²))
RMS_v = SQRT(AVG(vertical_vibration²))
```

**Step 3 — 偏差率计算**：
```
D_h = |RMS_h(当前) - RMS_h(基线)| / RMS_h(基线)
D_v = |RMS_v(当前) - RMS_v(基线)| / RMS_v(基线)
Deviation = max(D_h, D_v)
```

**Step 4 — 健康评分**（指数衰减模型）：
```
HealthScore = 100 × exp(-Deviation × 3)
```
结果约束在 [0, 100] 区间内。

**Step 5 — 健康等级分类**：

| 评分区间 | 等级标识 | 中文描述 | 颜色编码 |
|----------|----------|----------|----------|
| 80 – 100 | healthy | 健康 | `#52c41a` 绿色 |
| 60 – 79 | slight_degradation | 轻微退化 | `#faad14` 黄色 |
| 40 – 59 | moderate_degradation | 中度退化 | `#fa8c16` 橙色 |
| 20 – 39 | severe_degradation | 严重退化 | `#f5222d` 红色 |
| 0 – 19 | critical | 危险 | `#cf1322` 深红 |

### 4.3 轴承特征频率估算

基于滚动轴承经典运动学模型，估算轴承各元件的故障特征频率：

```
转频：        fr = rotating_speed_rpm / 60  (Hz)
外圈故障频率：BPFO = (N/2) × (1 − d/D × cosα) × fr
内圈故障频率：BPFI = (N/2) × (1 + d/D × cosα) × fr
滚动体故障频率：BSF = D/(2d) × (1 − (d/D × cosα)²) × fr
保持架故障频率：FTF = 1/2 × (1 − d/D × cosα) × fr
```

其中 N=8（滚动体数量），d=8mm（滚动体直径，估计值），D=40mm（节圆直径，估计值），α=0（接触角）。

### 4.4 FFT 频谱分析

系统实现了基于 DFT（离散傅里叶变换）的振动频谱分析功能：

- 从指定采样批次中提取最多 8192 个数据点
- 应用 Hann 窗函数抑制频谱泄漏：`w[i] = 0.5 − 0.5×cos(2πi/(N−1))`
- 计算 DFT 幅度谱，频率范围上限 2000 Hz（覆盖轴承故障特征频段）
- 同时输出水平通道和垂直通道频谱数据

**注意**：本系统使用纯 Python DFT 实现，适合原型验证。生产环境中建议使用 `numpy.fft` 替代以获得更高性能。

### 4.5 RUL 预测算法

**剩余使用寿命（RUL）预测**基于以下步骤：

1. **全生命周期 RMS 趋势提取**：对所有采样批次的水平/垂直 RMS 值进行时间序列聚合。
2. **退化率计算**：
   ```
   早期RMS = AVG(前3个批次的综合RMS)
   末期RMS = AVG(最后3个批次的综合RMS)
   总退化率(%) = (末期RMS − 早期RMS) / 早期RMS × 100
   每样本退化率 = 总退化率 / 总样本数
   ```
3. **RUL 样本数估算**：
   ```
   RUL_samples = 当前健康评分 / (每样本退化率 × 100)
   ```
4. **时间文本转换**：将样本数转换为人类可读的时间表述（年/月/天/小时/分钟）。
5. **退化阶段判定**：基于当前健康评分自动判定退化阶段并生成维护建议。

**维护建议策略**：

| 阶段 | 建议内容 |
|------|----------|
| 健康 | 轴承运行状态良好，按计划进行常规巡检即可。 |
| 轻微退化 | 轴承出现轻微退化迹象，建议加强监测频率，关注振动趋势变化。 |
| 中度退化 | 轴承退化趋势明显，建议安排预防性维修，准备备件。 |
| 严重退化 | 轴承退化严重，建议尽快停机更换，避免发生运行故障。 |
| 危险 | 轴承处于危险状态，必须立即停机更换！继续运行可能导致严重事故。 |

## 5. API 接口设计

### 5.1 接口设计原则

- RESTful 风格，JSON 格式响应
- 全局 CORS 支持（`Access-Control-Allow-Origin: *`）
- SQLite `SQRT` 函数自动注册
- 数据库连接超时 30 秒（`timeout=30`）
- 查询参数支持数据集筛选、故障类型筛选、关键词搜索

### 5.2 页面路由

| 方法 | 路由 | 认证 | 说明 |

| GET | `/` | 否 | 首页，已登录重定向至仪表盘，未登录重定向至登录页 |
| GET | `/login` | 否 | 登录页面 |
| GET | `/dashboard` | 是 | 系统仪表盘主页 |

## 7. 前端关键技术

### 7.1 请求超时与竞态控制

系统实现了完善的异步请求管理机制：

```javascript
// 15 秒超时的 fetch 封装
function fetchWithTimeout(url, timeoutMs = 15000, externalSignal = null) {
    const controller = new AbortController();
    const timeout = setTimeout(() => controller.abort(), timeoutMs);
    if (externalSignal) {
        if (externalSignal.aborted) { controller.abort(); clearTimeout(timeout); }
        else { externalSignal.addEventListener('abort', () => controller.abort()); }
    }
    return fetch(url, { signal: controller.signal }).finally(() => clearTimeout(timeout));
}
```

- **AbortController**：快速切换轴承时，前一个请求的 `AbortController` 被触发，旧请求立即取消，避免慢响应覆盖快响应（竞态条件）；
- **finally 块保障**：无论请求成功/失败/取消，`catch` 和 `finally` 块确保 `hideLoading()` 被调用，不会出现 loading 层永久旋转的卡死状态。

### 7.2 防抖（Debounce）

轴承选择下拉框应用 300ms 防抖，避免用户快速连续切换时触发多次图表刷新：

```javascript
document.getElementById('bearingSelect').addEventListener('change',
    debounce(onBearingChange, 300)
);
```

### 7.3 ECharts 加载层管理

- `showLoading(false)` 在 `clearCharts()` 顶部调用，确保清空图表前先移除加载层；
- `hideLoading()` 在 `refreshCharts()` 的 `finally` 块中统一调用；
- 清空图表时使用 `setOption({series: []}, true)` 的 `notMerge=true` 模式彻底清除旧数据；
- 所有图表更新函数设置 `title: null`，清除 ECharts 默认 merge 模式下残留的占位文字。

### 7.4 数据缓存策略

- 统计表格使用 `cachedStatsData` 保存聚合数据，翻页时直接从缓存切片渲染，无需重新请求；
- 仪表盘一次并行请求 3 个 API（`aggregate_stats` + `health_score` + `health_summary`），RMS 趋势从 `aggregate_stats` 中直接复用，不额外请求 `rms_trend` 端点。

### 7.5 响应式布局

- 侧边栏支持折叠/展开切换（`toggleSidebar()`）；
- CSS Grid 布局自适应：大屏 4 列统计卡片 → 中屏 2 列 → 小屏 1 列；
- 图表网格大屏 2 列 → 小屏 1 列；
- 所有 ECharts 实例监听 `window.resize` 事件自动重绘。

### 7.6 侧边栏导航

全局统一的侧边导航栏，包含：
- **主要功能**：系统仪表盘、对比分析、剩余寿命预测
- **数据浏览**：轴承列表、工作条件、故障类型
- **动态轴承列表**：显示前 30 个轴承的彩色圆点+编号+故障类型快速入口

## 8. 数据分析与健康评估

### 8.1 时域特征提取

系统对每个采样批次的振动数据提取以下时域统计特征：

| 特征 | 公式 | 物理意义 |
|------|------|----------|
| RMS（有效值） | SQRT(Σx²/N) | 振动能量大小，反映整体振动水平 |
| Peak（峰值） | MAX(\|x\|) | 最大瞬时冲击强度 |
| Peak-to-Peak（峰峰值） | MAX(x) − MIN(x) | 振动信号的总偏移幅度 |
| Mean（均值） | Σx/N | 传感器零偏参考 |
| Crest Factor（波峰因子） | Peak / RMS | 冲击性故障的敏感指标（正常 3–5，故障时显著增大） |

### 8.2 退化趋势分析

- **线性回归趋势线**：对 RMS 时间序列进行最小二乘线性拟合，输出退化趋势斜率；
- **分阶段对比**：将运行周期等分为 4 个阶段（初期/中期/后期/末期），对比各阶段的平均 RMS 和峰值变化，直观呈现加速退化特征。

### 8.3 频谱分析流程

```
时域振动数据 (Hann 窗口)
       │
       ▼ DFT
幅度频谱 (0 – 2000 Hz)
       │
       ▼ 特征频率匹配
 ┌─────┼─────┬──────────┬──────────┐
BPFO   BPFI   BSF        FTF       转频
(外圈) (内圈) (滚动体)   (保持架)   (1×)
```

故障诊断逻辑：频谱中在特定特征频率处出现明显峰值，可初步判断对应元件的故障类型。例如，外圈故障通常表现为 BPFO 频率及其谐波处的幅值升高。

## 9. 性能优化

### 9.1 数据库优化

| 优化项 | 优化前 | 优化后 | 提升倍数 |
|--------|--------|--------|----------|
| 复合索引 `(bearing_id, sample_index)` | 缺失（全表扫描） | 已创建（索引覆盖） | 覆盖所有 GROUP BY 查询 |
| 轴承列表 API（`/api/bearings`） | 超时 >10s（N+1 LEFT JOIN COUNT 子查询） | 约 2.1s | ~5× |
| 健康评分 API（`/health_score`，10 条） | 约 10.9s（每行关联子查询基线） | 约 141ms（2 步独立查询） | ~77× |
| 健康摘要 API（`/health_summary`） | 约 6.2s（13 次独立 SQL 扫描） | 约 2.3s（1 次 GROUP BY + CASE WHEN） | ~3× |
| 轴承详情 API（`/bearing/<no>`） | 4 个标量子查询 | 1 个 LEFT JOIN 聚合 | ~3× |

**核心优化手段**：
1. **消除关联子查询**：将每行依赖子查询的标量计算拆分为独立的基线查询 + 分组查询两步；
2. **查询合并**：`health_summary` 将早期/晚期/总体统计从多次独立扫描合并为单次 GROUP BY + CASE WHEN；
3. **SQRT 函数注册**：`conn.create_function("SQRT", 1, math.sqrt)` 解决 Windows SQLite 构建缺失 `SQRT` 的问题；
4. **启动时指数创建**：`ensure_indexes()` 在应用启动时自动创建性能索引，带 `try/except` 容错保护。

### 9.2 前端优化

| 优化项 | 说明 |
|--------|------|
| 请求合并 | 仪表盘从 4 个并行请求优化为 3 个（RMS 趋势复用 `aggregate_stats` 数据） |
| 竞态控制 | `AbortController` + `AbortError` 静默处理，避免旧请求覆盖新请求 |
| Loading 可靠性 | `finally` 块 + `clearCharts` 双重 `hideLoading` 保障，消除卡死 |
| 图表占位移除 | `setOption({title: null})` 清除 ECharts merge 模式残留的占位文字 |
| 分页缓存 | 统计数据表格翻页时复用已获取的全量聚合数据 |
| 采样模式 | `vibration_data` 提供 `sampled` 模式，通过 `rowid % step` 均匀采样约 2000 点 |

### 9.3 数据库维护

- `check_database.py`：快速检查数据库状态（表结构、轴承分布、数据总量）；
- `test_api.py`：7 个测试用例覆盖所有核心 API 端点，含正常请求和带参数请求。
