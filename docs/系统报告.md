## 1. 项目概述

### 1.1 背景与目标

轴承作为铁路列车运行的关键部件，其健康状态对铁路安全运输有重要影响。本系统基于 **XJTU-SY 轴承全生命周期数据集**构建了一个完整的铁路轴承健康状态分析原型系统，实现轴承振动数据的可视化分析、健康状态评估与多轴承对比分析。

### 1.2 核心功能

| 功能 | 说明 |
|------|------|
| 用户认证 | 基于 Session 的登录/登出系统，分角色（管理员/工程师/分析师） |
| 系统仪表盘 | 单个轴承的全景健康分析视图，6 个 ECharts 交互图表 + 健康评估报告 |
| 轴承详情 | 振动数据分页浏览、时域波形、FFT 频谱、RMS 退化趋势 |
| 对比分析 | 2-4 个轴承的 RMS/峰值/健康评分趋势对比、柱状图、雷达图 |
| 健康评估 | 基于 RMS 退化率的健康评分算法（0-100），自动分类健康状态 |

### 1.3 数据集规模

| 指标 | 数值 |
|------|------|
| 轴承总数 | 42 |
| 数据点总数 | 3.02 亿（302,069,188） |
| 数据库大小 | 31.4 GB |
| 工作条件 | 5 种 |
| 故障类型 | 14 种 |
| XJTU-SY 轴承 | 15 个（3 种工况 × 5 个轴承） |
| Gearbox 轴承 | 20 个 |
| 测试样本 | 7 个 |

## 3. 数据设计

### 3.1 数据库表结构

#### operating_condition（工作条件表）

| 字段 | 类型 | 说明 |
|------|------|------|
| id | INTEGER PK | 主键 |
| condition_name | TEXT UNIQUE | 条件名称 |
| radial_force_kN | REAL | 径向载荷 (kN) |
| rotating_speed_rpm | INTEGER | 转速 (rpm) |
| sampling_frequency_hz | INTEGER | 采样频率 (Hz) |
| sampling_points | INTEGER | 每批次采样点数 |
| sampling_period_min | INTEGER | 采样周期 (分钟) |

#### bearing_info（轴承信息表）

| 字段 | 类型 | 说明 |
|------|------|------|
| id | INTEGER PK | 主键 |
| bearing_no | TEXT UNIQUE | 轴承编号 |
| condition_id | INTEGER FK | 关联工作条件 |
| total_csv_files | INTEGER | CSV 文件总数 |
| total_data_points | INTEGER | 数据点总数 |
| lifetime_minutes | REAL | 寿命时长 |
| fault_element | TEXT | 故障元件 |
| fault_type | TEXT | 故障类型 |

#### vibration_data（振动数据表 · 核心）

| 字段 | 类型 | 说明 |
|------|------|------|
| id | INTEGER PK | 主键 |
| bearing_id | INTEGER FK | 关联轴承 |
| sample_index | INTEGER | 采样批次序号 |
| timestamp | TEXT | 采样时间戳 (ISO 8601) |
| horizontal_vibration | REAL | 水平振动加速度 (g) |
| vertical_vibration | REAL | 垂直振动加速度 (g) |

**关键索引：** `idx_vibration_bearing_sample ON vibration_data(bearing_id, sample_index)` —— 覆盖所有 GROUP BY sample_index 查询路径。

### 3.2 XJTU-SY 工作条件

| 条件 | 径向载荷 | 转速 | 转频 | 采样频率 |
|------|----------|------|------|----------|
| Condition_1 | 12 kN | 2100 rpm | 35 Hz | 25.6 kHz |
| Condition_2 | 11 kN | 2250 rpm | 37.5 Hz | 25.6 kHz |
| Condition_3 | 10 kN | 2400 rpm | 40 Hz | 25.6 kHz |

### 3.3 轴承命名规则

- **XJTU-SY**: `Bearing{工况}_{序号}`，如 `Bearing1_1` 表示工况 1 下的第 1 个轴承
- **Gearbox**: `Gearbox_{故障类型}_{转速}`，如 `Gearbox_ball_20` 表示滚珠故障、20Hz 转速

### 4.2 健康评估算法

系统采用基于 RMS 退化率的多维度健康评分模型：

```
健康评分 = 100 - Σ(退化惩罚因子)

退化率计算：
  D_h = (末期RMS_h - 初期RMS_h) / 初期RMS_h × 100%
  D_v = (末期RMS_v - 初期RMS_v) / 初期RMS_v × 100%

评分分类：
  80-100 → 健康
  60-79  → 轻微退化
  40-59  → 中度退化
  20-39  → 严重退化
  0-19   → 危险
```

**特征频率估算：** 基于轴承运动学模型计算 BPFO（外圈故障频率）、BPFI（内圈故障频率）、BSF（滚动体故障频率）、FTF（保持架故障频率）。

### 5.2 认证 API

| 方法 | 路由 | 说明 |
|------|------|------|

| POST | `/api/auth/logout` | 用户登出 |

### 5.3 数据 API

| 方法 | 路由 | 说明 |
|------|------|------|
| GET | `/api/statistics` | 系统统计概览 |
| GET | `/api/bearings` | 轴承列表（支持 dataset 筛选） |
| GET | `/api/bearing/<no>` | 轴承详情信息 |
| GET | `/api/vibration_data` | 振动原始数据（支持分页/时间筛选） |
| GET | `/api/bearing/<no>/aggregate_stats` | 聚合统计（RMS/峰值/峰峰值/波峰因子） |
| GET | `/api/bearing/<no>/health_score` | 健康评分时间序列 |
| GET | `/api/bearing/<no>/health_summary` | 健康评估综合报告 |
| GET | `/api/bearing/<no>/spectrum` | FFT 频谱数据 |
| GET | `/api/bearing/<no>/rms_trend` | RMS 趋势数据 |
| GET | `/api/operating_conditions` | 工作条件列表 |
| GET | `/api/health` | 服务健康检查 |

### 5.4 API 设计要点

- 所有 API 响应启用 CORS（`Access-Control-Allow-Origin: *`）
- 自动注册 `SQRT` 函数（SQLite 内建缺失）
- 数据库连接超时设置为 30 秒（`timeout=30`）
- 复合索引 `idx_vibration_bearing_sample` 覆盖核心查询路径

### 6.3 前端关键技术

- **AbortController + fetchWithTimeout**: 15 秒超时 + 可取消请求，防止快速切换轴承时竞态
- **防抖 300ms**: 轴承选择下拉框事件去抖
- **数据缓存**: 统计表格分页数据缓存复用，避免重复请求
- **showLoading/hideLoading**: ECharts 内置加载层管理，finally 块确保清除

## 7. 性能优化

### 7.1 数据库优化

| 优化项 | 修复前 | 修复后 | 提升 |
|--------|--------|--------|------|
| 复合索引 `(bearing_id, sample_index)` | 缺失 | 已创建 | 覆盖所有 GROUP BY 查询 |
| 轴承列表 API | 超时 >10s (N+1 查询) | **2.1s** | ~5× |
| health_score (10 条记录) | ~10.9s (关联子查询) | **141ms** | ~77× |
| health_summary | ~6.2s (13 次独立扫描) | **2.3s** | ~3× |
| `/api/bearing/<no>` | 4 个标量子查询 | 1 个 LEFT JOIN | ~3× |

### 7.2 前端优化

| 优化项 | 说明 |
|--------|------|
| 请求合并 | 移除冗余 `rms_trend` fetch，数据从 `aggregate_stats` 复用（4→3 并行请求） |
| 竞态控制 | AbortController 取消旧请求，避免慢响应覆盖快响应 |
| 加载层管理 | `showLoading(false)` 在 `finally` 块 + `clearCharts()` 中调用，确保加载层清除 |
| 分页缓存 | 统计表格翻页时复用已获取的聚合数据 |
| 图表占位移除 | `setOption` 中设置 `title: null` 清除初始化占位文字 |

### 7.3 后端优化

- **查询合并**: `health_summary` 从 13 次独立扫描合并为 1 次 GROUP BY + CASE WHEN
- **消除关联子查询**: `health_score` 拆分为 2 步独立查询（基线 RMS + 分组评分）
- **去除 N+1**: `/api/bearings` 移除 LEFT JOIN COUNT 子查询（超大数据集不必要）
- **SQRT 注册**: `conn.create_function("SQRT", 1, math.sqrt)` 解决 SQLite 缺函数问题

## 8. 已修复问题

### 8.1 Bug 修复

| 严重度 | 问题 | 根因 | 解决方案 |
|--------|------|------|----------|
| **致命** | 轴承详情页 4 图表永久卡死在"加载中" | `updateDistCharts()` 未定义导致 ReferenceError | 删除非法函数调用 |
| **高** | fetch 无超时导致 loading 永久旋转 | Promise.all 无超时无 AbortController | 添加 `fetchWithTimeout(15s)` + AbortSignal |
| **高** | 快速切换轴承时 loading 层不消失 | `clearCharts()` 不调用 `hideLoading()` | 在 `clearCharts()` 顶部添加 `showLoading(false)` |
| **高** | 竞态条件导致图表状态混乱 | `onBearingChange()` 不 await `refreshCharts()` | 改为 async/await + AbortController 取消机制 |
| **中** | 图表渲染后仍显示灰色占位文字 | `title` 属性从未被清除（ECharts merge 模式） | 所有图表更新函数添加 `title: null` |
| **中** | 数据库启动时加锁 | `ensure_indexes()` 在模块导入时阻塞 | try/except 保护 + 手动创建索引 |

### 8.2 SQRT 函数问题

SQLite 在 Windows 上的标准构建不包含 `SQRT` 函数。通过在 `get_db_connection()` 中注册 `math.sqrt` 解决。

## 10. 部署与运行

- Python 3.10+
- SQLite 3.x
- Flask（`pip install flask`）

### 10.2 启动步骤

```bash

cd railway-bearing_data_service

# 2. 启动 Flask 服务
python api/app.py

# 3. 访问系统
```

### 10.4 注意事项

1. **数据库体积**: `bearing_data.db` 约 31.4 GB，确保磁盘空间充足
2. **首次启动**: Flask 启动时会自动创建性能索引（`ensure_indexes()`）
3. **查询性能**: 核心查询已在 3 秒内完成，极大数据量查询（如全量振动原始数据）建议搭配分页使用
4. **并发**: 开发服务器（Flask 内建）仅供本地使用，生产环境建议使用 Gunicorn/uWSGI
